## Резюме
1. **Каталог пересчитан программно.** 8 непересекающихся корзин, итог ровно 14 716 URL, из них 6 077 в Merchant. Скрипт и CSV — во вложениях. У Gemini три ошибки: (а) SEG-1 = 4 209, а не 4 208; (б) 5 рисковых OOS посчитаны дважды (в SEG-3 и SEG-4); (в) из 6 273 URL без названия 181 входит в эвристических кандидатов, поэтому SEG-6 = 1 776 с названием + 6 092 без названия, а не 1 595 + 6 273. Модератор прав: 2 рисковых SKU в наличии и 5 не в наличии.
2. **Двухуровневая схема HIGH/LOW Gemini в предложенном виде небезопасна.** Google прямо пишет: если у кампании с высоким приоритетом кончился бюджет, ставку делает кампания следующего приоритета ([справка Google](https://support.google.com/google-ads/answer/6275296)). Значит, «жёстко ограниченный бюджет» HIGH гарантирует утечку общих запросов в LOW по высоким ставкам. Кроме того, минус-слова не покрывают близкие варианты, а предложенные общие минусы («ďalekohľad», «cena», «recenzie») при широком соответствии **полностью блокируют** модельные запросы вида «leica trinovid 10x42 hd cena». Таблица из 22 тестовых маршрутов во вложении.
3. **«100 % контроля модельных запросов» доказать нельзя.** Отчёт о поисковых запросах показывает только запросы, которые искало значительное число пользователей. Связку «запрос → конкретный offerId» API напрямую не отдаёт. Её можно получить только через группы объявлений с одним товаром.
4. **Экономика четырёх SKU посчитана параметрически.** При марже 25 % и CR рекламы 1 % безубыточная ставка за клик получается: Trinovid ≈2,15 €, Vegas ED ≈0,50 €, New Vegas ED ≈0,28 €, 150PDS EQ3 ≈0,87 €. **Это сценарий, а не ставка.** Коэффициенты бюджета 1,86/2,21 у Gemini посчитаны по неверной формуле; даже наивная правильная оценка — 2,12/2,41, и она не является прогнозом. Правило остановки «1,5×CM без покупки» в ≈22 % случаев остановит безубыточную модель.
5. **Предлагаю более простой переход:** сначала отдельная Standard Shopping-кампания для пилотной когорты, с группой на каждый контрольный SKU, без схемы HIGH/LOW. Включение по принципу «сначала новое, потом выключаем старое», с сохранённым снимком старого дерева для отката. Приёмка в три уровня: допуск → показы товара → показы по запросу. Пороги приёмки статистические, по всей когорте, а не по одному SKU.
6. **Блокеры запуска:** не проверены конверсии (R1-CHATGPT-02); нет живых listing groups и минус-слов; нет маржи; не решён вопрос с 107817/94399; нет решения владельца по изменениям во время праздничного сезона.

### Результат 2. Архитектура Shopping и модельного Search
**Вывод:** схему HIGH/LOW на старте не внедрять. Причины: утечка общих запросов при исчерпании бюджета HIGH (справка Google), необходимость подбирать минусы по словам на каждый вариант написания, блокировка модельных запросов широкими общими минусами. Предлагаю два этапа.

**Этап A — пилот без схемы HIGH/LOW (рекомендую):**
- Новая Standard Shopping-кампания `SK_SHOP_Models_Pilot` с отбором пилотной когорты (Результат 4). Приоритет **выше**, чем у старых Shopping-кампаний с теми же товарами: только это гарантирует, что после включения ставку делает новая кампания, и даёт порядок «сначала новое, потом выключаем старое».
- **Одна группа объявлений = один контрольный offerId** (и по одной группе на каждый близкий вариант семейства). Запросы группы = запросы товара. Это и есть механизм измерения KPI-C.
- Минусы: только точного соответствия на общие однословные запросы, и только после просмотра реальных запросов. Без «cena», «recenzie» без решения владельца.
- Ставки: ручная цена за клик на группу в пределах экономического потолка (Результат 3) после получения маржи. Автоматические стратегии — только после закрытия R1-CHATGPT-02. Утверждения о eCPC/tROAS не делаю (см. `05_`).
- PMax: если в аккаунте есть PMax с этими товарами — сначала карта пересечений (E2). При пересечении решает Ad Rank, а не приоритет. Для пилотных SKU пересечение с PMax нужно исключить, иначе измерение KPI-C смешается.

**Этап B — схема HIGH/LOW только для семейств, где в данных этапа A общие запросы заметно съедают бюджет:** бюджет HIGH не ограничивает показы (контроль ежедневно); минусы моделей в HIGH — отличительные слова по фактическим запросам; общие минусы в LOW — только точные; 22 маршрута прогнаны через Ad Preview до включения.

**Модельный Search `SK_SEARCH_Models`:**
- Одна модель/комплектация = одна группа = URL карточки. Ключи точного и фразового соответствия.
- Exact включает близкие варианты, поэтому перекрёстные минусы по семейству (размеры 8×42/8×32/10×25 для Trinovid; «new» в группе 26113; goto/synscan/eq5/ota/«150p» в группе 47420) обязательны.
- Без дублирования ключей между группами (R2-CLAUDE-08).
- RSA: заголовки ≤30 символов, описания ≤90, пути ≤15. Закреплять только H1. Цена и наличие — не статическим текстом.
- Search и Shopping по одному запросу могут показываться одновременно, это разные форматы. Цель «карточка + текстовое объявление» достижима, но измеряется раздельно.

Маршруты — `query_routing_tests.csv` (Q01–Q20 Shopping, S01–S02 Search). Проверка RSA — `rsa_check.csv`.

4. **Экономика:** вклад когорты после окна задержки конверсий, против контрольной группы (разность разностей).

**Технический триггер отката (не статистический):** уровень 1 не выполнен через 24 ч после T4, или после T6 у SKU в наличии нет допуска ни в одной кампании.

**Статистический триггер отката (когорта):** E = базовые показы когорты за тот же период дней недели × (изменение контрольной группы). Откат, если наблюдаемые показы < E − 2,58·√E за ≥3 дня подряд. Для одного SKU с <30 ожидаемыми показами за период триггер не применять.
