## 1. Главная фактическая поправка: account-level список НЕ пуст
**R5-CODE-12 отклоняю в заявленном виде.** Повторный GAQL:
1. campaign_shared_set: 18 связей; все у PAUSED/REMOVED кампаний. Эта часть Code верна.
2. customer_negative_criterion: есть критерий типа NEGATIVE_KEYWORD_LIST.
3. Его negative_keyword_list.shared_set указывает на ENABLED shared_set типа ACCOUNT_LEVEL_NEGATIVE_KEYWORDS.
4. Прямое чтение shared_criterion для именно этого shared_set возвращает **258 слов**, включая BROAD kde, lacno, popis, ake, aký, funguje, keyword_text.
5. Отдельный повторный запрос трёх слов kde/lacno/popis подтвердил и их, и тип ACCOUNT_LEVEL_NEGATIVE_KEYWORDS.

Следовательно, отсутствие campaign_shared_set у активных кампаний **не доказывает отсутствие account-level минусов**. Google связывает account-level список через CustomerNegativeCriterion, не через CampaignSharedSet [S1]. Эти слова наследуются и SO27: «не переносить в новые списки» недостаточно.

Есть диагностическая несогласованность: shared_set.member_count возвращает 0, тогда как прямые shared_criterion возвращают строки. Причину несогласованности в этом ходе не установил; нулевой счётчик нельзя ставить выше реально прочитанных элементов и ссылки. Перед применением повторить прямое чтение и сверку UI/другим API-клиентом, не удалять весь список вслепую. В customer_negative_criterion также присутствуют content labels, mobile app categories и placements: весь ресурс тем более не пуст.

Campaign-level чтение у ENABLED возвращает свои минусы Search; ad-group-level — пустой результат. Это **не** отменяет наследуемый список. Сами слова в исторических shared sets ≠ действующий список; в ходе 4 я правильно требовал проверки всех уровней, но не завершил доказательство связи. В ходе 6 эта связь проверена.

[Обезличенный протокол чтения](06_chatgpt_attachments/negative_scope_evidence.json) содержит запросы, результаты и ограничение member_count, без идентификаторов кабинета.

**Новый preflight SO27:**
- реальный account-level diff по решениям хода 4/5, включая снятие вредных слов, а не создание пустого «аналога»;
- затем SO27-shared/shop/search/no-hunting и их реальные прикрепления;
- effective negatives = account + прикреплённые shared + campaign + group;
- проверить положительные fixtures по каждому маршруту. Не прикреплять старый «Универсальный» целиком.
- запрет иностранных языков не принимаю без построчного перечня: венгерский запрос жителя Словакии не автоматически мусор. Проверять географию присутствия, смысл, доставку и фактический расход.

### Price ≥20: сейчас не реализовано
В обычных ListingDimensionInfo Standard Shopping нет числового фильтра price ≥20 [S2]. Нельзя написать «label3/price» и считать защиту готовой. p_0_49 включает и <20, и 20–49,99.
Предпочтение: после проверки зависимостей разделить ценовую метку на p_lt20 / p_20_49 и остальные существующие диапазоны; все paid-деревья исключают p_lt20, missing и неизвестные значения, включая допустимые старые fallback-маршруты во время overlap. Проверить 19,99 / 20 / 49,99 / 50 €, скидочную effective price, обновление цены и метки, EUR, рассинхронизацию. Альтернатива — валидированный item_id allowlist с обязательным обновлением, но не статический список «навсегда».
Free listings остаются; согласен, что destination-исключение необязательно, **если** paid-фильтры действительно охватывают каждый возможный маршрут. До этого R5-04 открыт.

### 72 часа: контрольное окно, не автоматическое отключение
- Новые Shopping HIGH=2, старая база LOW=0: механизм приоритетов принимаю только для одинакового товара/страны, при доступности нового маршрута.
- Старый LOW может подхватить товар/запрос, не допущенный новым HIGH. До overlap нужны совместимые исключения hold/цены/опасных запросов и продуманный допустимый fallback. Иначе новая защита обходится старым маршрутом.
- Для каждого старого пула: проверить доступность нужных SKU, работающие leaf bids/ads, покрытие new vs old, показы/клики/ошибки tracking, оставшиеся пропуски. Один новый SKU с кликом не основание выключить всю старую категорию.
- Через 72 часа решить по каждому пулу. Готовый переключить; неготовый — не расширять автоматически, пересчитать расход и вернуть на разбор. Не продолжать overlap сверх выделенного потолка без решения.
- Откат возвращает только ранее допустимые маршруты с исправленными минусами/hold/price; «включить старое как было» не принимаю.
- Exact/phrase Search не даёт гарантии показа каждого буквального запроса; приоритет Shopping не заменяет семантику.

### Native total budgets и fallback
Чтение поля total_amount_micros **не доказывает возможность создания конкретного объекта** выбранным клиентом. Документация Google поддерживает Standard Shopping/Search с manual CPC [S3]. Исполнимый payload: period=CUSTOM_PERIOD, total_amount_micros, explicitly_shared=false, даты начала/окончания; amount_micros не задаётся одновременно. Предварительно validate-only/проверка UI без создания и включения. После разрешённого создания PAUSED — readback типа, суммы, дат, валюты.
Fallback из Code «те же daily budgets, ежедневный контроль» **отклоняю как равнозначный hard cap**: период пересекает месяцы, суточный расход может удвоиться [S4]. Если native вариант недоступен — новый ограниченный план и выбор владельца, не молчаливый переход.
Столбец after 21.12 — отдельное предложение: существующую total-budget кампанию нельзя просто переключить в daily 15 €/день. Нужен отдельный январский план/кампания или согласованное продление с новым lifetime cap. Сейчас он не авторизован.

### Перераспределение: изменить правила §4
- Порог ROAS =1,23/m — только пример при 23% налога и конкретном определении маржи. Для реальных решений нужен net contribution после себестоимости, переменных расходов, возвратов; VAT брать из заказа. Не обещать прибыль по gross ROAS.
- «≥25 кликов без покупки → исключить» отклоняю как универсальное правило. При истинном CR=2% вероятность нуля покупок после 25 кликов ≈60%, после 40 ≈45%. Для дорогих товаров есть лаг. Цена 200 € сама по себе не определяет требуемую выборку.
- До доказанной экономики: контролируемый loss budget на SKU/группу, purchase-only tracking, лаг созревания, расход/допустимая CPA, качество запроса. Нерелевантность исключается сразу, отсутствие продажи — не минус-слово.
- 40 кликов/ROAS ниже половины порога — сигнал проверить, не автоматическая массовая ставка −30%. Понижение ставки допускается после проверки отслеживания и лага; редкий продающий SKU не обнулять из-за календаря.
- «ROAS выше порога + budget lost >50% → +25%» только как предложение из доступного резерва/переноса, не автоматическое увеличение общего T. Прежде подтвердить несколько созревших покупок, наличие/маржу и отсутствие концентрации результата в одном заказе.
- На каждом изменении: charged_to_date + разрешённые remaining caps всех новых/заменённых кампаний + legacy/Predajňa allowance ≤ T. Уменьшение донора и увеличение получателя согласовать с уже потраченным; закрытые кампании не исчезают из реестра.
- 7 дней — первая коммерческая оценка, 48–72 часа — техническая доставка/мусор, а не статистическая окупаемость. «30+ покупок → smart bidding» также не универсальный порог готовности.
- Оценка cost × (1−lost_rank)/IS не является потолком спроса/бюджета. Метрики охватывают разные доступные аукционы, доли могут быть ограниченными <10%/>90%, а предельная стоимость/CR меняются. Оставить как грубый sensitivity scenario, не обоснование объёма расходов.
