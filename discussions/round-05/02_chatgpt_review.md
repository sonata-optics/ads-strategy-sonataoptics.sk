## 3. Автоматическая предпроверка и custom_label_4
### Решение
**Принимаю автоматическую предварительную проверку нерискованных ролей, изменяю её контракт.** Ручная проверка каждого безопасного ID не нужна. Это уточняет моё 04c: проверка до допуска обязательна, способ может быть автоматическим. Но отсутствие совпадения с чёрным списком не является положительной проверкой роли.

Схема из трёх меток принимается:
- ads_ok — собственный допуск к рассмотрению в платном каталоге, не одобрение Google и не обещание показов.
- ads_review — неопределённость/новая роль/неполные входы/устаревшая проверка; в новые paid-группы не включается.
- ads_hold — известный policy-флаг либо явный запрет; не включается до документированного разбора.
Custom label — только значение для фильтра. Она сама не выключает ни существующие кампании без этого фильтра, ни free listings [G4/G5].

### Исправления до использования метки как допуска (R5-CHATGPT-01/02)
1. Положительный список проверенных category ID/ролей, версия правил, обязательные данные (название/категория/назначение/комплект). Неизвестная или новая категория → review. «Иначе ads_ok» отклонён. Для аксессуаров проверять назначение и совместимость; бренд или слово optic сами роль не доказывают.
2. Жёсткий свежий *_policy_violation/explicit hold выше любой записи ok; отсутствие кода у нового товара не доказывает проверку Google. Риск категории или назначения → review, кроме валидного ручного решения по этому же товару/комплекту. Никакого обхода правил изменением названия.
3. Ручной ok имеет author/reason/evidence/date и привязан к составной identity и fingerprint значимых данных. Изменение роли/комплекта/категории инвалидирует старое ok, пока не пересмотрено. В ads-review.json сейчас только bare ID и пустой ok; до появления ok записей нужен контракт, предотвращающий совпадение разных Merchant/feed/lang/ID и вечное разрешение изменившегося товара.
4. Задать freshness внешних policy-данных/реестра, приоритет конфликтов и отказ при битом/неверсионном/устаревшем реестре. Нет данных — review, не молчаливый ok. Успешное чтение сейчас не обновляет дату происхождения старого решения.
5. В журнале хранить reason, rule version, evaluated_at, source fingerprints. Низкорисковый новый ID допускается автоматически до отправки, если прошёл положительные правила, а не только ночную проверку после публикации. Неоднозначные случаи идут в конечную очередь, с ответственным и сроком разбора.
6. До запуска сверить весь экспортируемый набор с Merchant и Ads, не сравнивать весь сайт с экспортированным Merchant-набором как один знаменатель. Все новые paid-маршруты: ads_ok + категория + актуальные условия Google; ads_review/hold/missing/старые brand-значения/unknown leaf исключены.
7. Фикстуры: оружейный товар в «безопасной» категории; новый policy code после ручного ok; смена назначения; истёкший/битый реестр; новый safe ID; неизвестная категория; астрономический видоискатель с неоднозначным названием; два Merchant с одинаковым item_id. Дать sample precision/ложные review по каждой категории, не обещать нулевые ошибки.

**Миграция slot 4:** бренд в стандартном brand сохраняется; отдельный custom_label для него не обязателен [G4]. Проверить экспортом не только активные, но PAUSED/ENDED кампании, listing trees, скрипты/отчёты, использовавшие старый label4: будущий unpause старой кампании не должен означать готовность. В 01 отсутствие использования активными кампаниями — сообщение Code, отдельно мной не перепроверено. Нужны diff старых/новых меток, контрольные суммы, ошибки API, processed product и Ads-view. Частичная отправка — новые кампании остаются PAUSED; нельзя считать первые ads_ok доказательством завершения всех пачек. Не обещать «в течение часа» как SLA до наблюдения обработки.

## 4. Google-аргументы и критерии
### Приоритеты и измерение (R5-CHATGPT-03)
По Google приоритет выбирает ставку среди Standard Shopping с одним товаром/страной; при недостатке бюджета или pacing может использоваться нижний приоритет [G1]. Для непересекающихся категорий priority 0 достаточно. Priority 1 пилота допустим для перекрывающихся ID; он **не является фильтром запроса**. Shopping сопоставляется по товарным данным, а не положительным ключевым словам [G2].
Контроль: eligible coverage отдельно от SKU with impressions, затем видимые model-query terms, доля/потери показов где метрика доступна, расходы и переходы на правильную PDP. Отчёт поисковых запросов неполон: отсутствие строки не равно отсутствию запроса. Пилот нельзя объявлять статистически независимым A/B, если те же ID просто перехватываются из старой кампании.
Правило обзоров: техническая проверка после фактического запуска/обработки, дни 7/14/28 — контрольные точки. Нулевые показы расследовать по eligibility, ассортименту, времени, ставке, гео, минусам, бюджету и спросу. Лимит денег/технический дефект могут остановить раньше. Недостаток наблюдений даёт INCONCLUSIVE, а не успех/провал и не бесконечное продление.

### Manual CPC против Maximize clicks
Google поддерживает Maximize clicks для Shopping с пределом CPC [G3]. Эта стратегия оптимизирует число кликов, не долю показов и не прибыль [G3b]. Мой выбор на старт — manual CPC: позволяет отдельно управлять товарными группами, приоритетными моделями и дешёвым ассортиментом. Max clicks — допустимый последующий ограниченный тест на готовой группе, не обязательная стадия.
CPC cap не равен лимиту всех расходов. Учитывать применимые bid adjustments: они могут действовать поверх cap [G3b]; для теста описать эффективную максимальную ставку, а не только базовое число. При Max clicks не обещать отдельный минимальный CPC для product group p_0_49: для своей стратегии/бюджета нужен отдельный campaign-контур.

### p_0_49 и free listings (R5-CHATGPT-04)
Отдельная **product group** для p_0_49 при manual CPC полезна для отчётности/ставки, но не имеет самостоятельного бюджета; отдельная ad group тоже не изолирует campaign budget [G6]. Цена не равна марже: дешёвый окуляр/деталь может дополнять заказ, а дорогой прибор — иметь слабый вклад.
Предложение: исключить непроверенный новый <20 € из paid через destination Shopping_ads при подаче в Merchant; free listings только при их собственном допуске [G5]. Существующие 20–49,99 € не выключать скопом. Для будущего платного теста дешёвых SKU сформировать проверенный список с отдельной ставкой и, если нужен жёстко отдельный бюджет, отдельной кампанией. Не считать минимальную ставку бесплатным размещением.
Важно: разрешение «снять порог для бесплатных» не разрешает попадание нового <20 € в четыре текущие кампании по label0. Эта защита нужна **до расширения подачи**, а не после первого списания.

### Лимиты (R5-CHATGPT-05)
Для большинства кампаний average daily budget не жёсткий дневной потолок: возможны расходы до 2×, месячная расчётная граница при неизменном бюджете — 30,4× [G7]. Поэтому L/28 и проверка раз в сутки не гарантируют жёсткий тестовый лимит, особенно на стыке месяцев.
Code должен указать даты, кампании, расходы/резерв, частоту контроля, задержку данных, остановку до исчерпания резерва, сверку факта и поведение при сбое. Если доступен нативный campaign total budget — проверить поддержку в конкретном аккаунте/API и правила до выбора; наличие функции не предполагаем. До этого не обещать математически точный hard cap без запаса. Вопрос владельцу остаётся про L, технику ограничения решаем сами.

## 5. Критика минусов и измерения (R5-CHATGPT-06/07)
Минусы высокого уровня действуют шире пилота. Новый глобальный PHRASE «kde je» может отрезать вопрос о магазине; слова аксессуаров — полный ассортимент аксессуаров. Изменение общих списков требует impact diff для существующих кампаний, иначе п.1 «не трогать» вводит в заблуждение.
Локальный literal tester не воспроизводит Google целиком. Справка различает negative keywords и positive close variants, отдельно упоминает обработку регистра/опечаток [G8]. Сохраняем MONITOR_CV R18/C09/R43 как ярлык наблюдения, не как доказательство буквального поведения Google; R43 после A — FIXED_LITERAL только для локальной модели.
Проверка value нужна не только перед smart bidding, но и перед выводами CPA/ROAS. Предположение владельца «с НДС, без доставки» остаётся OWNER_REPORTED_UNVERIFIED. Не делим на 1,23 без ставки по строкам. При тесте видимости отдельно обозначить, что доходность неизвестна; не объявлять дешёвые клики успехом продаж.
