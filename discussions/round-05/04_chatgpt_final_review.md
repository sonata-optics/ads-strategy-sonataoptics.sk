Дополнительный статический аудит:
- Кэш reg/pol один на процесс, не по контексту. Нужны ключ merchant+language+feed+channel+пути и тест второго контекста.
- policySweep считает строки, а не уникальные composite ID; порог seen ≥1000 не доказывает полный снимок. Нужны контроль всех страниц, повторных токенов, дублей, схемы ответа, резкого падения покрытия против последнего полного снимка; частичный результат не снимает предыдущие hold.

- 3-дневная свежесть не заменяет предзапусковой policy-check и событийного удержания ранее запрещённого товара.
- Это критика конкретной реализации. Положительный список безопасных категорий и автоматическая предпроверка остаются правильным направлением; не возвращаем ручной просмотр каждого безопасного аксессуара.

Дополнительные выводы:
- У основных Shopping и категорийного Search потери доли показов по бюджету существенно выше потерь по рейтингу. Это повод изучить бюджет и распределение SKU, не просто повысить CPC. Метрики условны относительно доступных аукционов; граничные значения <10%/>90% не трактовать как точные.
- Последняя неделя дала больше атрибуционных покупок при меньшем расходе, но выручка почти не выросла. Рост сезона принимаю как бизнес-вводную владельца; эти четыре недели с изменявшейся рекламой не доказывают причинный рост всего рынка.
- Подтверждённые покупки есть по запросам о телескопах для наблюдения звёзд, конкретных моделях, туристических биноклях и даже подарке ребёнку. Нельзя вырезать весь категорийный/подарочный спрос ради «только точных моделей».
- В товарах виден пример детского микроскопа с покупками, но слабой экономикой, и пример детского телескопа с лучшим соотношением покупок к расходу. Поэтому «детское» не единый выключатель.
- Нулевые покупки после нескольких кликов не доказывают мусорный запрос. Минусовать по нерелевантности; снижение ставки/пауза по расходу и допустимой CPA — другая операция.
- Последние запросы: top 100 по расходу, товары top 60, плюс отдельный purchase-only срез. Это не полная перепись всех запросов. Товарные строки суммировать по campaign + composite product ID, не по меняющемуся title.

До оценки прибыли сверить существующий заказ с offline upload, tax, shipping, refunds и дублями. **Не ждать первого будущего заказа теста.** Gross/value из кода не равен проверенному событию. Финансовые пороги считать на одинаковой базе: net revenue без НДС и доставки против net-маржи; gross ROAS показывать отдельно. Применять фактическую ставку налога заказа, не делить весь ассортимент на константу без проверки.

### Search и Marketing Miner
01b полезен для расширения категорий, но часть частот восстановлена по ширине графиков; отдельные проверки не делают весь ряд точным экспортом. Объёмы похожих запросов не складывать в уникальную аудиторию.
«0–10 в MM» не равно статусу LOW_SEARCH_VOLUME Google Ads. Сохранять готовое модельное ядро и проверять реальный статус; точечный Search добавлять для приоритетных моделей с запасом/маржой, не запрещать все новые модельные группы заранее.
Начало — manual CPC со ставками по группам и контролем effective modifiers. 0,20–0,30 € из Code — стартовые гипотезы, а не рыночная истина. Для 20–49,99 € отдельный осторожный bid; формула экономической границы CPC = допустимая CPA × подтверждённая purchase CR. Нет маржи/CR — ограниченный тест, не выдуманный оптимум.
Maximize clicks с лимитом CPC допустим как отдельное сравнение позже; он оптимизирует клики, не продажи, и может выбирать дешёвый невыгодный ассортимент. tROAS пока нет: смешаны цели и не подтверждена база value.

## 6. L: отклонение старой гарантии, новый сезонный план
**R5-05 не закрыт.** D=0,8L/28 плюс резерв 20% и ежедневная проверка не доказывают ограничение произвольных 28 дней, особенно через границу месяцев. Дата окончания ограничивает время, не сумму. Правило «cost ≥ X» по отдельной кампании не считает общий L. Нельзя обещать фиксированную задержку данных 3 часа без проверки.

В актуальной документации Google [S1–S3] **campaign total budget доступен новым Standard Shopping и Search**, в том числе manual CPC, на период 3–90 дней. Он ограничивает начисляемую сумму за срок, **но не дневной расход**. Тип бюджета существующей кампании на этот режим не переключается. Это более подходящий способ для сезонного L.

Предлагаю:
- L — дополнительные расходы на 28 дней новых сезонных кампаний, включая выбранных продавцов-SKU, новый Junior, pilot и Search. Старая база B отдельно и не увеличивается автоматически.
- Новые кампании готовить с total budgets суммарно 0,8L; 0,2L — нераспределённый резерв владельца, а не деньги, доступные системе.
- Следующий Code обязан проверить поддержку в конкретном кабинете/пути создания, способ чтения total_amount и start/end, не создавать live объекты. Если текущий коннектор не поддерживает — подготовить точный UI/Editor/API план, не выдавать daily budget за total.
- Суммарно уже начисленное + оставшиеся утверждённые лимиты всех новых/заменяющих кампаний ≤ L. Не перезапускать 28-дневный счётчик при замене кампании. Перераспределение только с учётом потраченного и резервирования, не одновременное дублирование лимитов.
- Контроль темпа ежедневно, alerts 80/90% и аварийная пауза — дополнительная защита, не доказательство hard cap. Для daily-budget fallback нужен явно описанный операционный риск; консервативный вариант суммарного неизменного D≤L/56 при обычном лимите 2D и 28 днях, с проверкой применимости и без увеличений бюджета. Его нельзя незаметно заменить более агрессивным D.
- Выбранный срок привязать к сезонному календарю и последней дате гарантированной доставки, а не растягивать невостребованный тест. Через 48–72 часа проверить доставку/мусор, через 7 дней перераспределять разрешённый остаток; не ждать 28 дней, чтобы заметить поломку.
