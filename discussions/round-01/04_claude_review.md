## Резюме
1. **Google-фид не полностью «чистый».** По URL пересечение `scope-candidates.json` и Merchant действительно равно нулю. Но построчная проверка Merchant находит 2 SKU высокого риска (оружейная оптика под названием «монокуляр») и 5 SKU среднего риска (ИК-подсветки для прицелов). Один из high-risk SKU стоит 5 000 € и есть в наличии.
2. **`scope-candidates.json` неполон.** Ещё ≈276 URL с признаками оружейной оптики в него не попали: коллиматоры, термопредсадки, крепления, пистолетные площадки, ИК-подсветки. Поэтому фильтр по стоп-словам (denylist) для Meta и Google недостаточен. Нужен разрешительный список (allowlist) по `product_role`.
3. **Ложные срабатывания тоже есть.** 4 термобинокля ATN BinoX 4T названы в фиде как «Ďalekohľad 4T … 4.5-18x», то есть как прицел. Три зрительные трубы Meade названы «zameriavací» (прицельный). Это ошибки названий, а не нарушения. Их нужно переименовать, а не исключать.
4. **Юнит-экономика:** фреймворк с НДС 23 %, эквайрингом, логистикой и возвратами ниже. Главный вывод: из-за фиксированных затрат на заказ безубыточный ROAS для недорогих товаров получается очень высоким. Это 28 % товаров Merchant в наличии (дешевле 100 €). Сегментировать нужно по вкладу заказа, а не по цене.
5. **Факт-чек Gemini:** утверждение о приоритете PMax над Standard Shopping устарело. С октября 2024 года их конкуренцию решает Ad Rank. Ставка 23 % подтверждена.
6. **Главный риск:** запустить Meta- или PMax-каталог по стоп-словам и пропустить предсадки, коллиматоры и «мультифункциональные» тепловизоры.

Консенсус не объявляю. Рекламу не меняю.

### Задача 2. Фреймворк юнит-экономики (CPA / ROAS / PNO) с DPH 23 %

**Параметры заказа** (источник для каждого — CS-Cart / бухгалтерия; публиковать только сценарии):

| Символ | Что это |
| --- | --- |
| `P_g` | Сумма товаров заказа с DPH (без доставки) |
| `t` | Ставка DPH по SKU (обычно 0,23) |
| `P_n = P_g / (1 + t)` | Выручка без DPH |
| `m` | Валовая маржа на `P_n` = (P_n − COGS) / P_n |
| `f` | Комиссия эквайринга, % от **P_g** (берётся с суммы с налогом) |
| `S_out`, `S_back` | Доставка к клиенту / обратная доставка, которую несёт магазин |
| `D_n` | Оплаченная клиентом доставка без DPH (0 при бесплатной) |
| `H`, `H_ret` | Обработка заказа / обработка возврата |
| `r` | Доля возвратов (14-дневный отказ + брак) |
| `d` | Уценка вернувшегося товара, доля от COGS |
| `π` | Требуемая прибыль после рекламы на заказ (€) |

**Формулы.**
```
COGS          = P_n × (1 − m)
CM_exp        = (1 − r) × (P_n − COGS + D_n) − f × P_g − S_out − H − r × (S_back + H_ret + d × COGS)
Max CPA       = CM_exp                         (безубыточно)
Target CPA    = CM_exp − π
BE ROAS (net) = P_n / CM_exp                   (value в Ads = товары без DPH, все заказы включая будущие возвраты)
BE ROAS (gross)= P_g / CM_exp = BE ROAS(net) × 1,23    (если value передаётся с DPH — так делать не надо)
tROAS         = P_n / (CM_exp − π)
Max PNO       = CM_exp / P_n                   (для Heureka: PNO = cost / выручка без DPH)
Max CPC (BE)  = CM_exp × CR_site               (CR = покупки / сессии GA4, не конверсии/клики)
Target CPC    = Target CPA × CR_site
```
Всё считается на уровне **заказа** (средний чек по сегменту), а не цены SKU. Возвраты уже учтены в `CM_exp`, поэтому value в Ads не нужно дополнительно корректировать, если используется эта формула. Если загружаются корректировки на возвраты, `r` из формулы убирается.

**Сценарий чувствительности** (не прогноз; цены — **факт**, медианы Merchant IN_STOCK; остальное — **допущения**: f = 1,5 %; S_out 5/7/12 €; H 3/3/4 €; r 6/5/4 %; H_ret 5/5/10 €; d 10/10/15 %; D_n = 0):

| Сегмент (медиана с DPH → без DPH, n SKU) | Маржа m | Max CPA | BE ROAS (value без DPH) | BE ROAS, если value с DPH | Max PNO |
| --- | --- | --- | --- | --- | --- |
| A: телескопы/микроскопы ≤300 € (170 € → 138 €, n=261) | 20 % | 14,5 € | 9,55 | 11,75 | 10,5 % |
| A | 30 % | 27,5 € | 5,02 | 6,17 | 19,9 % |
| B: бинокли 300–800 € (449 € → 365 €, n=121) | 20 % | 50,9 € | 7,17 | 8,82 | 13,9 % |
| B | 30 % | 85,8 € | 4,26 | 5,23 | 23,5 % |
| C: тепловизоры ≥1 500 € (2 410 € → 1 959 €, n=50) | 15 % | 219,6 € | 8,92 | 10,97 | 11,2 % |
| C | 25 % | 408,9 € | 4,79 | 5,89 | 20,9 % |

Полная сетка с маржой 15–35 % считается тем же расчётом. Её можно пересчитать на реальной марже.

**Выводы из модели.**
1. При одинаковой марже безубыточный ROAS сегмента A на 15–50 % выше, чем у B и C: около 10 € фиксированных затрат на заказ (доставка, обработка, эквайринг, возвраты) съедают заметную часть маржи на чеке 170 €.
2. Пример A: m = 30 %, CR 1 % (сценарий) → безубыточный max CPC ≈ 0,28 €. При CR 0,5 % → 0,14 €.
3. Требование «10 % чистой прибыли от выручки без DPH» резко поднимает планку: в примерах A при 30 %, B при 25 % и C при 20 % tROAS получается 10,1 / 11,5 / 16,6. Целевую прибыль лучше задавать в € на заказ или как долю от `CM_exp`.

**Правила применения.**
1. Сегментировать по `CM_exp`, а не по цене. Простой `custom_label` по бакетам вклада: `cm_low` (<15 €), `cm_mid` (15–60 €), `cm_high` (>60 €). Бакет считается в закрытой среде, в фид уходит только метка.
2. `cm_low` не участвует в привлекающих Shopping/PMax. Только наборы, порог бесплатной доставки, кросс-продажи, Heureka с PNO ≤ Max PNO.
3. Smart Bidding (tROAS) включать только при Primary = purchase (без НДС) и ≥30–50 покупках за 30 дней на кампанию. Ниже — ручная или eCPC-логика по max CPC.
4. Стоп-критерий кампании: 2 периода подряд (по 14 дней) фактический ROAS (value из CS-Cart, без DPH) < BE ROAS сегмента.
5. LTV не закладывать, пока нет когорт по повторным покупкам. По умолчанию LTV = первый заказ.
6. **Шоурум / B2B-лиды** (R1-GROK-03): `Max CPL = Max CPA × P(лид → оплата)`. Вероятность конверсии берётся только из CRM/журнала (лид → визит/демо → заказ CS-Cart). Пока журнала нет, для лидов — CPL как наблюдаемая метрика без оптимизации.

### Задача 3. Алгоритм проверки каннибализации (item_id-кампании и custom_label_0)

**Определение.** SKU каннибализируется, если он (а) **допущен** в ≥2 активные кампании и (б) **фактически получал показы** в ≥2 кампаниях за один период. Совпадение названий кампаний доказательством не является.

**Шаг 1. Состав допуска (eligibility) на уровне кампаний** — Google Ads API, только чтение:
```sql
-- 1a. Campaign listing scope (inventory filter)
SELECT campaign.id, campaign.name, campaign.status, campaign.advertising_channel_type,
       campaign.shopping_setting.campaign_priority, campaign.shopping_setting.feed_label,
       campaign_criterion.listing_scope.dimensions, campaign_criterion.negative
FROM campaign_criterion
WHERE campaign_criterion.type = 'LISTING_SCOPE'

-- 1b. Standard Shopping: дерево product partitions
SELECT campaign.id, ad_group.id, ad_group.status, ad_group_criterion.status,
       ad_group_criterion.negative, ad_group_criterion.listing_group.type,
       ad_group_criterion.listing_group.parent_ad_group_criterion,
       ad_group_criterion.listing_group.case_value.product_item_id.value,
       ad_group_criterion.listing_group.case_value.product_custom_attribute.index,
       ad_group_criterion.listing_group.case_value.product_custom_attribute.value,
       ad_group_criterion.cpc_bid_micros
FROM ad_group_criterion
WHERE ad_group_criterion.type = 'LISTING_GROUP'

-- 1c. PMax: фильтры групп объявлений
SELECT campaign.id, asset_group.id, asset_group.status,
       asset_group_listing_group_filter.type, asset_group_listing_group_filter.parent_listing_group_filter,
       asset_group_listing_group_filter.case_value.product_item_id.value,
       asset_group_listing_group_filter.case_value.product_custom_attribute.index,
       asset_group_listing_group_filter.case_value.product_custom_attribute.value
FROM asset_group_listing_group_filter
```
Плюс Merchant: `offerId → custom_label_0…4, feedLabel, availability, статус в Shopping ads`. В публичной выгрузке меток нет; их нужно выгрузить отдельно.

**Шаг 2. Матрица допуска E[item, campaign].** Для каждой активной кампании (campaign, ad group и asset group ENABLED, бюджет > 0) прогнать каждый offerId через listing scope → дерево партиций до листа. Лист «Everything else» с исключением (excluded) = не допущен. Отрицательный узел = не допущен. Результат: таблица `item_id × campaign` с 0/1.

**Шаг 3. Фактическая подача:**
```sql
SELECT segments.date, segments.product_item_id, segments.product_custom_attribute0,
       campaign.id, campaign.advertising_channel_type,
       metrics.impressions, metrics.clicks, metrics.cost_micros, metrics.conversions, metrics.conversions_value
FROM shopping_performance_view
WHERE segments.date BETWEEN '2026-08-16' AND '2026-11-13' AND metrics.impressions > 0
```
`shopping_performance_view` охватывает и Standard Shopping, и PMax ([документация](https://developers.google.com/google-ads/api/docs/shopping-ads/reporting)). Поле `segments.product_custom_attribute0` фиксирует значение метки **на момент показа**, поэтому смена меток во времени учитывается.

**Шаг 4. Классификация SKU.**

| Класс | Условие | Действие |
| --- | --- | --- |
| Доказанное пересечение | E ≥ 2 **и** показы в ≥2 кампаниях в одну неделю | Развести: исключить item_id из одной кампании (отрицательный узел или listing scope) |
| Потенциальное | E ≥ 2, показы только в одной | Не трогать. Наблюдать. Проверить priority и Ad Rank |
| Нет пересечения | E ≤ 1 | — |
| Нулевая подача | E ≥ 1, показов 0 | Проверить статус в Merchant/`shopping_product.issues` до любых выводов |

**Шаг 5. Кто выигрывает.** Standard vs Standard — campaign priority, затем ставка. PMax vs Standard — **Ad Rank** (с октября 2024). Пересечения поисковых запросов проверять через `search_term_view` по обеим кампаниям.

**Шаг 6. Ущерб.** Для доказанных SKU сравнить CPC и долю показов до и после старта второй кампании с контрольной группой SKU без пересечения (разность разностей). Решение о слиянии или паузе — только по этой разнице и BE ROAS сегмента.

**Выход:** `discussions/round-02/…/cannibalization_check.csv` (item_id, campaigns_eligible, campaigns_served, класс, рекомендация). Без клиентских данных.
