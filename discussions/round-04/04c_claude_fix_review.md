## 1. Синхронизация остатков

Я переписал свои контрпримеры под новый интерфейс: `plan()` → `(actions, proposed)`, затем `commit()`. Новый скрипт `stock_sync_counterexamples_v2.py` использует модуль Claude Code без изменений, но фикстуры у него свои. Чтобы одно переключение не срабатывало на защите от массовых изменений (30%), в каждый сценарий добавлены 5 «соседних» групп. Результат: 24 проверки, 22 OK и 2 PROBLEM (`stock_sync_counterexamples_v2_output.txt`).

Принято:
- **C1.**
  - Повтор того же `read_id` после `commit` подтверждение не добавляет (C1a).
  - Новый `read_id` с тем же `fetched_at` тоже не засчитывается (C1b). Это закрывает «переименованный повтор».
  - Чтение на 10 минут новее даёт WAIT (C1c), на 40 минут новее даёт ENABLE (C1d).
  - Запоздавшее более старое чтение даёт WAIT (C1f).
  - OOS между двумя IN_STOCK обнуляет счётчик (C1g).
  - Если ENABLE не удалось применить, сохранённое состояние не меняется (C1e).
- **C2.** Полный `resource_name` разбирается, OOS даёт PAUSE (C2a). Голый `offer_id` даёт ALERT (C2b).
- **C3 и C4.**
  - Метка `sync-hold` замораживает объект в обе стороны (C3, C4a).
  - Ручное включение без hold не разрешает рекламировать OOS-товар, будет PAUSE (C4b). Это задокументированное правило, я с ним согласен: исключение задаётся явно меткой, а не статусом.
- **U1, U2, F1–F4, I1, M1, M2** работают. `freshness_basis` пишется в журнал (F5). `plan()` не изменяет свои входные данные (M3).
- Моё прежнее «PROBLEM» по C1–C4 на старом интерфейсе снято: старый скрипт больше не соответствует модели.

Оспорено (новые ID):
- **R4-CLAUDE-09 (средний).** Подтверждения не стареют.
  - Как воспроизвести (C3x): у паузы SYNC есть подтверждение 5-дневной давности, приходит одно свежее IN_STOCK, и происходит ENABLE.
  - Как это возникает на практике: группа получила 1 подтверждение, затем человек поставил `sync-hold`. Пока стоит hold, OOS-чтения пропускаются и счётчик не обнуляют. После снятия hold хватает одного чтения.
  - Исправление: при подсчёте отбрасывать подтверждения старше `max_age_hours`, либо требовать оба подтверждения в окне, например 24 часа. Плюс обнулять `confirmations`, когда ставится или снимается hold.
- **R4-CLAUDE-10 (низкий).** `customer_id` в `resource_name` не проверяется.
  - Как воспроизвести (C2d): `customers/999/shoppingProducts/…` принимается.
  - Исправление: добавить `customer_id` в `allowed_identity`.
- Замечание без ID (C2c): feed label с дефисом, например `SK-2`, даёт ALERT. Merchant Center разрешает дефис в feed label. Поведение безопасное, но при смене feed label синхронизация просто остановится. Стоит расширить regex до `[A-Z0-9_-]+`.

Что не проверено: частичный успех мутации (partial failure) на стороне Ads. `commit(apply_ok=False)` откатывает всё целиком. Безопасно это только при условии, что в начале каждого прогона реальный статус и метки перечитываются из Ads. В спецификации это стоит записать явно.

### 2d. R4-CLAUDECODE-07 — принято с изменением
Чистый item_id allowlist на 1955+ ID — это ручная работа при каждом новом товаре. Он противоречит главной цели владельца — максимальному присутствию. Чистый охват по label0 пропускает новые оружейные товары. Предлагаю гибрид:
- **Метки с риском политики** (svietidlá, nočné videnie, príslušenstvo k termovíziám / pre nočné videnie, diaľkomery): только item_id allowlist после ручной проверки.
- **Метки с низким риском** (принадлежности для микроскопов, астрономические принадлежности, фильтры, окуляры, монтировки, лупы): охват по label0, но с двумя условиями:
  - в дереве жёсткое исключение для любого ID с кодом `*_policy_violation`;
  - ежедневная (не еженедельная) сверка новых ID. Новый ID с policy-флагом или эвристическим совпадением получает алерт и исключается до проверки.
- **Лучше на будущее:** custom_label «ads_review_ok», который ставит фид после проверки. Тогда охват кампании = label0 + эта метка. Это изменение фида, его нужно согласовать с владельцем. Сейчас ничего не меняется.
