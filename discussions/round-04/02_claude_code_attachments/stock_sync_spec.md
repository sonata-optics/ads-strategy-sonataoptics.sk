# Синхронизация наличия → Search-группы: спецификация
Claude Code, круг 4; v2 (04b, 15.11) после C1–C4; **v3 (04d, 25.11)** после R4-CLAUDE-09/10 и 04d пп. 1, 2, 8. **Не внедрено и не подключено к API.** Модель [stock_sync_dryrun.py](stock_sync_dryrun.py): 45/45 сценариев (C1–C4, C3x, W1–W3, H1/H2, C2a–C2i, P1/P2 как регрессии), журнал — [stock_sync_dryrun_log.csv](stock_sync_dryrun_log.csv), итоги — [stock_sync_dryrun_results.csv](stock_sync_dryrun_results.csv).

## 1. Что синхронизация делает и чего не делает
- Управляет **только** модельными Search-группами из allowlist (сейчас 4: AG_103933, AG_26113, AG_103640, AG_47420).
- **Не трогает Shopping.** OOS-товар в Merchant сам становится NOT_ELIGIBLE (подтверждено: 47424/47412/47458). Фид передаёт наличие правдиво; товар не удаляется из фида только из-за OOS.
- Не меняет бюджеты, ставки, ключи, объявления, фид.
- Не использует отсутствие показов как признак OOS. Единственный источник наличия — поле availability Merchant (или CS-Cart, если владелец выберет его основным, — тогда та же логика).

## 2. Идентичность товара и контекст аккаунта
Составной ключ `merchant_id ~ channel ~ content_language ~ feed_label ~ offer_id`, например `5831333799~ONLINE~sk~SK~103933`. Принимаются две формы: голый ключ и полный `customers/<id>/shoppingProducts/<ключ>`; обе разбираются и проверяются по всем полям. **Неизвестный формат → ALERT, без действия** (C2b).
- **Аккаунт (R4-CLAUDE-10):** разрешённый `customer_id = 9492722541`. Чтение обязано нести `customer_id` этого аккаунта, иначе ALERT на весь запуск (C2h, C2i). Каждый управляемый объект несёт `ads_customer_id` из доверенного объекта Ads; отсутствует или чужой → ALERT (C2f, C2g). Полный resource_name с другим customer → ALERT (C2c). К короткому ключу customer **не дописывается молча**: он принимается только при доверенном контексте объекта.
- **Feed label** может содержать `-` и `_` (Merchant Center это допускает), но после разбора сравнивается с настроенным набором: `SK-2` принимается, только если он в списке (C2d), иначе SKIP (C2e). `offer_id` один — не ключ: тот же ID в AT/CZ-фиде не влияет на SK-группу (S10).

## 3. Состояние управляемого объекта
| Поле | Значения |
| --- | --- |
| status | ENABLED / PAUSED (фактическое из Ads на момент запуска) |
| pause_owner | `null` / `SYNC` / `MANUAL` / `REVIEW` |
| labels | `paused-by-sync` ставит только синхронизация при своей паузе; **`sync-hold` ставит человек**: объект заморожен в обе стороны (C3, C4a) |
| confirmations | список `{read_id, observed_at}` подтверждений IN_STOCK; хранится вне планировщика и меняется только после подтверждённого применения. **Подтверждения стареют:** при каждом подсчёте отбрасываются старше `confirmation_window_hours` (проектное значение 6 ч, равно пределу свежести, не бизнес-SLA) и датированные будущим (W1–W3, C3x) |
| hold_seen | предыдущее наблюдённое состояние `sync-hold`. Если сейчас hold установлен или снят, история подтверждений сбрасывается (H1, H2) |
| allowlisted | true только для явно перечисленных групп |

`pause_owner` определяется по change history (хранится ~30 дней). Последняя смена не синхронизацией → MANUAL. **Неизвестный владелец паузы не разрешает включение** (U1); `SYNC` без метки `paused-by-sync` трактуется как неизвестный (U2). Новая группа, созданная PAUSED для ревью, получает `REVIEW` и никогда не включается автоматически (S07).
Ручное включение группы без `sync-hold` **не разрешает рекламу OOS**: при OOS синхронизация снова ставит паузу (C4b). Намеренно держать группу включённой при OOS можно только меткой `sync-hold` — это явное решение человека.

## 4. Правила решения
| Вход | Действие |
| --- | --- |
| kill switch ON | ничего (S05) |
| ошибка API / таймаут | ничего, alert (S02) |
| пустой ответ | ничего, alert: пустой ответ ≠ всё OOS (S03) |
| нет read_id (происхождение неизвестно) | ничего, alert (F2) |
| время чтения в будущем (> 5 мин) | ничего, alert (F1) |
| fetch старше 6 ч (параметр) | ничего (S04) |
| upstream-время товара старше 6 ч при свежем fetch | ничего по объекту (F3) |
| метка `sync-hold` | ничего в обе стороны (C3, C4a) |
| товар отсутствует в ответе | alert, без действия (S09) |
| OUT_OF_STOCK, группа ENABLED | PAUSE + label `paused-by-sync` (S01) |
| OUT_OF_STOCK, группа PAUSED | ничего |
| IN_STOCK, PAUSED, owner SYNC + метка | ENABLE после 2 подтверждений из **разных read_id**, второе наблюдение новее первого минимум на 30 мин (S08, S16). Повтор того же чтения не засчитывается (C1); слишком близкое — тоже (I1). Неизменное корректное наличие не мешает: смена хеша не требуется |
| IN_STOCK, PAUSED, owner MANUAL/REVIEW | ничего, никогда (S06, S07) |
| IN_STOCK, ENABLED, но висит label | только снять label (человек включил вручную) (S13) |
| PREORDER / BACKORDER | без автоматического включения, нужно правило владельца (S14) |
| вне allowlist | ничего (S11) |
| за запуск меняется > 30 % allowlist и ≥ 2 объектов | HALT, ручное подтверждение (S12) |

### Свежесть: upstream vs fetch
Если чтение содержит время обновления товара в источнике (`upstream_updated_at`), свежесть считается по нему; иначе — по времени запроса, и журнал пишет `freshness_basis=fetch_time` (более слабое доказательство: fetch может вернуть давно не обновлявшиеся данные). Доступность upstream-поля в выбранном API — НЕТ ДАННЫХ, проверить при внедрении.

### Ограничение: hold между опросами
Если человек поставил и снял `sync-hold` между двумя запусками, по текущим статусам/меткам это не видно, и сброс истории не произойдёт. Закрывается только событиями с происхождением (Ads `change_event` по метке ad group, с временем и автором) или журналом изменений меток; без них — признанное ограничение. Окно 6 ч уменьшает, но не устраняет риск.

## 5. Чистый планировщик, идемпотентность, журнал, dry-run
- `plan()` не меняет входные объекты (проверяется во всех сценариях) и возвращает действия + **предлагаемое** состояние. `commit()` применяет его только после подтверждённого применения; при HALT (M1) или ошибке применения (M2) сохранённые подтверждения не продвигаются.
- Повтор с тем же входом после commit не даёт действий (S15).
- **Частичный успех (04d п. 8):** `commit()` принимает результат по каждому объекту. Объект с неуспешным или неизвестным результатом не меняет сохранённое состояние и помечается `needs_reconcile` (P1). Весь batch одним флагом «успех/неуспех» не считается.
- **Сверка перед каждым циклом:** `reconcile()` перечитывает реальные статусы и метки групп в Ads; наблюдаемое состояние побеждает сохранённое. PAUSED без метки `paused-by-sync` получает владельца UNKNOWN и никогда не включается; история подтверждений при расхождении сбрасывается (P2).
- Журнал на каждое решение: run_id, время, объект, identity, решение, причина, действие, hash входа; хранить ≥ 90 дней.
- Режимы: `dry_run` (по умолчанию, только журнал) → `apply` только после ревью журнала владельцем. Первые 2 недели — только dry_run.
- Аварийное отключение: флаг kill switch в конфиге проверяется первым; отключение не откатывает прошлые действия, их откат — по журналу.

## 6. Откат
Снять паузу можно только для объектов с `pause_owner=SYNC` по журналу. Откат восстанавливает статусы, но не гарантирует немедленных показов.

## 7. Нужные данные (без секретов)
| Данные | Источник | Поля |
| --- | --- | --- |
| Наличие | Merchant API products / Ads `shopping_product` | identity, availability, время чтения |
| Статусы групп | Ads `ad_group` | id, status, labels |
| Кто менял | Ads `change_event` | resource, user/client, время |
| GTIN/MPN, destinations (E10) | Merchant API products (полная карточка) | gtin, mpn, destinationStatuses — для фида, не для sync |
Ключи и токены хранятся вне репозитория.

## 8. Открыто
Частота запуска, порог свежести, число подтверждений, порог HALT, источник истины (Merchant или CS-Cart) — параметры для владельца. Синхронизация Shopping-структуры не нужна при включении OOS-товаров в allowlist пилота (см. [migration_checklist.md](migration_checklist.md)).
