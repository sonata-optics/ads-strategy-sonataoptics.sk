## Уточнения к отзыву Cowork
1. **Value.** Каноническая методика уже содержит «без НДС и доставки». Добавляю ещё явную строку о базах всех порогов. Отклоняю универсальное «если тег с НДС, порог ×1.23»: это работает только при единой ставке 23%, отсутствии иных различий (доставка/скидки/возвраты) и той же выборке. Фактическое value тега пока UNKNOWN.
2. **MONITOR_CV.** Принимаю для текущего состояния R18/C09/R43 вместо NO_CHANGE_NEEDED. Но R43 в варианте A уже PASS благодаря явной правке: сохранить отдельно current_resolution=MONITOR_CV и proposed_resolution=FIXED_LITERAL, а не потерять исправление. R18/C09 остаются наблюдением/решением владельца. MONITOR_CV не означает, что negative keywords расширяются как positive keywords.
3. **solarna.** Пример solarna nabíjačka без диакритики действительно содержит минус solarna. Нельзя на этом основании утверждать гарантированную блокировку solárna nabíjačka с диакритикой. Добавить обе формы, буквальный результат и неопределённость отдельно; примеры из каталога не выдавать за реально зарегистрированные поисковые запросы.
4. **bresser.de.** Подсказки не готовы к утверждению всей пачкой. В bresser_role_hint.csv 26916 Zoom monokulár и 26917 Monokulár BRESSER классифицированы как астрономические принадлежности: regex okulár совпал внутри monokulár. Числа 150/26/10/8/76 — результат грубой эвристики, не проверенная разбивка. Роль предмета имеет приоритет над словами принадлежностей; исправить границы/порядок и пересчитать.
5. **Частичный успех.** Перед каждым будущим циклом перечитывать реальные статусы/метки Ads; подтверждать применение по каждому объекту, не считать весь batch успешно/неуспешно применённым одним флагом. Сейчас только модель/спецификация.

Источники Google, проверены 15.11: [negative keywords](https://support.google.com/google-ads/answer/2453972), [feed labels](https://support.google.com/merchants/answer/14994087). Feed label с дефисом допустим синтаксически; это не разрешает произвольный label: после парсинга всё равно сравнивать с configured allowlist.

## R4-CLAUDECODE-07 — гибрид принят с обязательной предварительной проверкой
Принимаю **как целевую архитектуру**, не разрешение менять фид:
- Спорные роли/метки: только проверенные item_id по составной identity, с явным решением по роли/политике.
- Остальные: категория + явный признак ads_review_ok, выставляемый после проверки. Свободный custom_label слот выбрать только после инвентаризации: не перезаписывать используемую метку.
- Любой новый ID и существенное изменение роли/комплекта по умолчанию PENDING; без допуска не попадает в рекламируемое множество. Policy flag отзывает проектный допуск, а не маскируется названием.
- До появления такого механизма использовать генерируемый из проверенного реестра item_id allowlist, обновляемый пакетно. Это не требует ручного ввода тысяч ID.
- Ежедневная сверка — дополнительный контроль дрейфа. **Отклонён** вариант «новый SKU сразу рекламируется по label0, через день проверяем»: остаётся интервал непроверенного допуска.
- Изменения существующих живых товаров/кампаний вне разрешения. Жёсткий policy-флаг означает блокировку проектного добавления/расширения до разбора, не автоматическое удаление из Merchant.
